# Офлайн-развёртывание на РЕД ОС 8 (закрытый контур)

Ни `pip install`, ни `npm install` без интернета не работают — оба тянут
пакеты с внешних реестров. Схема ниже: один раз собрать всё необходимое на
машине с интернетом (ваш текущий Windows-компьютер), перенести один архив
на закрытый контур и установить там без какого-либо сетевого доступа наружу.

На РЭД ОС 8 не нужен ни Node.js, ни доступ к dnf-репозиториям с интернетом —
только уже установленный `nginx` (из локального репозитория/установочного
диска РЕД ОС) и работающий сервер PostgreSQL, к которому есть доступ по сети.

Python 3.11 не берётся из репозиториев РЕД ОС (в базовой поставке РЕД ОС 8
обычно не гарантирован пакет именно 3.11) — вместо этого в бандл
зашивается самодостаточная сборка CPython 3.11
([python-build-standalone](https://github.com/astral-sh/python-build-standalone)),
которая просто распаковывается в `/opt` и ничего не устанавливает в систему.

## Шаг 1. На машине с интернетом (Windows)

1. Откройте страницу релизов
   https://github.com/astral-sh/python-build-standalone/releases и найдите
   самый свежий файл вида

   ```
   cpython-3.11.<x>+<дата>-x86_64-unknown-linux-gnu-install_only.tar.gz
   ```

   (обычная сборка — без `-debug`, `-noopt`, `freethreaded` в имени).
   Скопируйте прямую ссылку на файл.

2. Из корня репозитория запустите:

   ```powershell
   powershell -ExecutionPolicy Bypass -File deploy\redos8\build-bundle.ps1 -PythonStandaloneUrl "<ссылка из п.1>"
   ```

   Скрипт:
   - скачивает portable Python;
   - скачивает все Python-зависимости бэкенда в виде готовых `.whl`
     (`pip download --platform manylinux_2_28_x86_64 ... --only-binary=:all:`
     — без компиляции на этапе установки на РЕД ОС);
   - собирает фронтенд (`npm run build`) в статику;
   - копирует исходники бэкенда и конфиги установки;
   - упаковывает всё в
     `deploy\redos8\dist\vacation-planner-offline-bundle-<дата>.tar.gz`.

   Требования на этой машине: Python 3.11 (тот же, что уже используется для
   `backend\.venv`), Node.js/npm, `tar.exe` (встроен в Windows 10/11).

   Если дев-машина не Windows, а Linux/macOS/WSL — используйте
   `deploy/redos8/build-bundle.sh <URL>` (тот же результат).

## Шаг 2. Перенос

Скопируйте получившийся `.tar.gz` на закрытый контур (флешка/другой
согласованный канал). Один файл — там уже всё нужное для установки.

## Шаг 3. На РЕД ОС 8

Предварительно должны быть доступны (уже есть на закрытом контуре, отдельно
от этого бандла):
- пакет `nginx` (установить из локального репозитория: `dnf install nginx`,
  если ещё не установлен);
- работающий PostgreSQL и данные для подключения к нему.

Установка:

```bash
mkdir vacation-bundle
tar xzf vacation-planner-offline-bundle-<дата>.tar.gz -C vacation-bundle
cd vacation-bundle
sudo ./install.sh
```

`install.sh` идемпотентен — его можно перезапускать (например, после того
как отдельно доустановили `nginx`). Он:

1. распаковывает portable Python в `/opt/vacation-planner/python`;
2. копирует исходники бэкенда и статику фронтенда;
3. создаёт venv и ставит зависимости офлайн (`pip install --no-index
   --find-links=wheelhouse ...`);
4. создаёт `backend/.env` из шаблона, если его ещё нет (**не
   перезаписывает** при повторном запуске);
5. накатывает миграции Alembic;
6. ставит и запускает systemd-юнит `vacation-backend` (uvicorn на
   `127.0.0.1:8000`, от отдельного системного пользователя `vacation`);
7. настраивает nginx (раздача `frontend-dist` + проксирование `/api/*` на
   бэкенд — та же схема, что и dev-прокси в `vite.config.ts`), включая
   типовые поправки SELinux (`httpd_can_network_connect`,
   `restorecon` на каталог статики) и открытие портов 80/443 в firewalld,
   если он активен.

### HTTPS через корпоративный сертификат (.pfx)

Если сервер в домене и у вас уже есть выданный доменным CA сертификат в
формате `.pfx`/`.p12` (обычно так и выдаёт Windows CA) — nginx можно сразу
поднять на HTTPS с ним, без Let's Encrypt и без ручной конвертации.

Скопируйте `.pfx` на сервер РЕД ОС (тем же каналом, что и сам бандл) и
запустите установку с двумя переменными окружения:

```bash
sudo TLS_PFX_PATH=/root/server.pfx TLS_PFX_PASSWORD='пароль-от-pfx' ./install.sh
```

`TLS_PFX_PASSWORD` можно не указывать, если у файла нет пароля. `install.sh`
сам:
- сконвертирует `.pfx` в пару PEM (`server.crt`/`server.key`) через `openssl
  pkcs12` — nginx не умеет читать PKCS#12 напрямую (пробует без `-legacy`,
  при ошибке — с `-legacy`, это нужно части `.pfx`, выпущенных старыми
  Windows CA с RC2/3DES-шифрованием);
- положит их в `/opt/vacation-planner/tls/` (ключ — права `600`, только
  root);
- поднимет nginx на 443 с этим сертификатом, а 80 — просто редирект на
  443 (см. `nginx-vacation-tls.conf`).

Без `TLS_PFX_PATH` всё работает как раньше — обычный HTTP на 80
(`nginx-vacation.conf`). Сам `.pfx`-файл после установки можно удалить с
сервера — он использован только для конвертации, дальше nginx читает уже
готовые PEM-файлы.

Обратите внимание: HTTPS здесь — это сертификат **самого сервера** (шифрует
канал), а не аутентификация пользователей. Кто именно вошёл — по-прежнему
решает `AUTH_PROVIDER` (см. ниже про Kerberos/SPNEGO — вход по учётной
записи домена, которой пользователь залогинен на своём ПК).

### После установки — обязательно

Отредактируйте `/opt/vacation-planner/app/backend/.env`:

- `DATABASE_URL` — реальная строка подключения к PostgreSQL;
- `CORS_ORIGINS` — реальный адрес, с которого открывают приложение (при
  этой схеме — тот же origin, что и nginx, поэтому CORS фактически не
  используется, но пусть будет корректным);
- `AUTH_PROVIDER` — по умолчанию `dev` (вход под тестовым пользователем,
  без реального SSO). Для боевой эксплуатации — `kerberos` (Kerberos/SPNEGO
  через AD-домен `corp.amurgpz.ru`). Оставлять `dev` в проде — осознанный
  временный шаг, не забудьте про него.

#### Kerberos — какой режим выбрать (`KERBEROS_MODE`)

Два режима реализованы оба, переключение — одной переменной, без правок
кода. Разница в том, какой уровень проверяет сам SPNEGO-тикет:

1. **`KERBEROS_MODE=nginx`** — тикет проверяет nginx через модуль с
   директивами `auth_gssapi_*` (образец конфига —
   `nginx-gssapi.conf.example` в этой папке). Бэкенд Kerberos вообще не
   касается: не хранит keytab, не требует `python-gssapi`. Работает,
   только если у вас на сервере уже есть (или можно поставить) такой
   модуль nginx — стандартная сборка `nginx.org` его не включает, это
   отдельный пакет (в RHEL-семействе обычно вида `nginx-mod-auth-gssapi`).
   Проверить прямо на сервере:
   ```bash
   dnf list --available | grep -i auth-gssapi
   ls /usr/lib64/nginx/modules/ 2>/dev/null | grep -i gssapi
   ```
   Если ничего не находится ни в одном подключённом локальном
   репозитории — этот режим недоступен без сборки модуля из исходников,
   используйте `python` вместо него.

2. **`KERBEROS_MODE=python`** — тикет проверяет сам бэкенд через пакет
   `python-gssapi`, используя `KERBEROS_KEYTAB_PATH`. nginx в этом случае
   — обычный прозрачный прокси. У `python-gssapi` нет готовых
   manylinux-колёс на PyPI (пакет линкуется с системной библиотекой
   Kerberos) — для офлайн-бандла его нужно собрать отдельно:
   - на машине с сетевым доступом **и той же версией glibc, что на РЕД
     ОС 8** (проще всего — временная РЕД ОС 8 виртуалка/контейнер)
     поставьте `krb5-devel gcc python3-devel` из локальных репозиториев,
     затем соберите колесо под тот же портативный Python 3.11, что в
     бандле:
     ```bash
     /opt/vacation-planner/python/bin/python3.11 -m pip wheel gssapi -w /tmp/gssapi-wheel
     ```
   - скопируйте получившийся `.whl` в `wheelhouse/` бандла (рядом с
     остальными зависимостями) до запуска `install.sh` — он подхватит
     его автоматически (см. шаг 3 в списке установки выше), но не
     упадёt, если файла нет (тогда `KERBEROS_MODE=python` работать не
     будет, а старт сервиса явно скажет об этом в логе — см. ниже).

В обоих режимах нужно заполнить `KERBEROS_SERVER_HOSTNAME` (конкретное
имя сервера, часть SPN вида `HTTP/<hostname>@CORP.AMURGPZ.RU`) — когда
IT выдаст keytab под конкретный хост. `KERBEROS_KEYTAB_PATH` нужен только
в режиме `python` (в режиме `nginx` keytab лежит у nginx, не у бэкенда —
путь указывается прямо в конфиге nginx, `auth_gssapi_keytab`).

Если конфигурация Kerberos неполная или битая (нет `python-gssapi`, не
задан `KERBEROS_SERVER_HOSTNAME`, keytab не читается) — сервис
`vacation-backend` не запустится и явно скажет, чего не хватает:
```bash
sudo systemctl status vacation-backend
sudo journalctl -u vacation-backend -n 50
```

После правки `.env`:

```bash
sudo systemctl restart vacation-backend
```

### Проверка

```bash
curl http://127.0.0.1:8000/health        # бэкенд напрямую
curl http://<адрес-сервера>/health       # через nginx
```

Приложение — `http://<адрес-сервера>/` в браузере.

### Обновление версии в будущем

Повторите шаг 1 на машине с интернетом (после изменений в коде), перенесите
новый архив, распакуйте и запустите `install.sh` заново — он безопасно
обновит код, зависимости и статику поверх текущей установки и применит
новые миграции. Существующий `.env` не будет тронут.

## Файлы в этой папке

| Файл | Назначение |
|---|---|
| `build-bundle.ps1` / `build-bundle.sh` | Собрать офлайн-бандл на машине с интернетом |
| `install.sh` | Установка/обновление на РЕД ОС 8 |
| `nginx-vacation.conf` | Шаблон конфига nginx, HTTP (статика + прокси `/api`) |
| `nginx-vacation-tls.conf` | То же самое, но HTTPS — используется вместо предыдущего, если `install.sh` запущен с `TLS_PFX_PATH` |
| `nginx-gssapi.conf.example` | Образец `location /api/` для KERBEROS_MODE=nginx (не устанавливается автоматически) |
| `vacation-backend.service` | Шаблон systemd-юнита бэкенда |
| `.env.example` | Шаблон `backend/.env` для продуктива |
